# 打印机 0.3.39：凭空放置、光源与实机吞吐

默认开启的凭空放置原先仍优先点击相邻支撑块，导致可直接点击的空气目标被错误的放置面判断挡住。现在先点击目标空气格；原版方块需要支撑时再回退到相邻面。普通无朝向方块和光源使用眼睛附近的合法面内命中点，不再固定点击面中心。球形扫描先覆盖所有可能在眼睛交互距离内的方块，再用眼睛到方块立方体的真实距离过滤；执行阶段也不再使用目标中心加半格的错误早退。

`minecraft:light` 的物品携带原版 `BlockStateTag` 等级，放置预测按原版 NBT 应用顺序核对。不同亮度分到不同材料批次，避免 level 10 与 level 15 混排导致反复换手。单人创造可以复制精确物品栈；生存和多人模式不会凭空合成带标签物品。

在 Minecraft 1.20.1 单人创造、22 区块视距、原始星空树投影与存档的隔离副本上，独立验收驱动确认眼睛 5 格内有 128 个可放置且缺失的目标（59 个棕色混凝土、69 个亮度 10 光源）。间隔、每 tick 上限与冷却均为 0，凭空放置开启。每次从独立存档副本启动；30 tick 后在集成服务端线程核对完整方块状态，而不把客户端交互接受数冒充为完成数。

| 工作预算 | 单 tick 发出 | 服务端正确完成 | 打印耗时 | 客户端 tick 耗时 |
|---|---:|---:|---:|---:|
| 8 ms | 52 / 128 | 52 / 128 | 8.16 ms | 9.07 ms |
| 16 ms | 128 / 128 | 128 / 128 | 11.67 ms | 12.62 ms |

因此新设置的默认工作预算改为 16 ms，并将开发实例中原有的 8 ms 配置调整为 16 ms。其他已有配置中明确保存的 8 ms 仍然受尊重，用户可自行调回。16 ms 用例的 128 个目标均无需重试或等待换手；69 个光源的服务端状态均为 level 10。详细输入、隔离与计数见 [验收记录](../validation/printer-0.3.39/README.md)、[8 ms 原始结果](../validation/printer-0.3.39/result-8ms.json)和[16 ms 原始结果](../validation/printer-0.3.39/result-16ms.json)。

首次冷执行原先只能在一 tick 发出 1 个。新实现于模组启动时预热纯数据扫描/队列，进入世界后分刻做 16 次原版混凝土与光源的只读预测；预热不调用换手、放置、发包，也不修改世界。当预热完成、三项节奏均为 0 且工作预算为 16 ms 时，整个客户端生命周期只给第一次打印 tick 一个 32 ms 的有界启动额度。已明确设置较低预算的用户不受此加时影响；后续暂停重启继续按 16 ms 运行。

最终 0.3.39 构建的独立实机验收：首次 tick 发送 **128/128**，服务端正确完成 **128/128**，打印耗时 28.31 ms，整个客户端 tick 29.33 ms；同一进程停止后重新开始、重置这 128 格的热态 tick 再次完成 **128/128**，打印 12.01 ms、整个 tick 12.88 ms。无重试、等待换手或未知格。正式候选上一小修版本另做三次独立冷启动，均为 128/128，最慢客户端 tick 32.40 ms；最终小修仅限制启动加时只能使用一次。预热没有发施工包，观察区域与库存前后不变；最终验收中只读预测的最大单片为 5.11 ms。见[最终原始结果](../validation/printer-0.3.39/result-final.json)与[三次重启记录](../validation/printer-0.3.39/repeat-1.json)。

这证明给定玩家场景一 tick 的发送与最终服务端状态，并不保证任意机器、任意投影或多人服务器都在一 tick 完成；没有对持续 FPS 或 180° 转头做游戏验收。单个原版调用不能中途截断，预算并非硬实时界限。首刻约 29–32 ms 是明确的单帧成本。测试窗口和世界均是隔离副本，原始存档与投影文件未修改。
