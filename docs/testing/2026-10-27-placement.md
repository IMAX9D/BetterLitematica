# 1.20.1 邻接与分步放置修复

构建版本：`0.4.17-placement-fix`。对应报告 `BL-20261027-8CA60CDAB778`，以及用户补充的打开栅栏门、墙、玻璃板与乌托邦对角连接行为。

## 原因

报告记录多次 `sent=0`、大量重试并停留在“等待可用放置面”；同期背包补货已有成功回包。源码中，放置预测要求方块状态与投影一致，因而把“放下后由邻居生成连接”和“先关闭放置、后右键打开”的正常中间状态一并拒绝，最终返回无放置面。

检查乌托邦实际 JAR 后还发现，Diagonal Blocks 会把栅栏和玻璃板物品对应的方块替换为另一注册 ID，并增加四个对角连接属性。仅忽略原版四个连接方向仍会被不同方块 ID 拦截。

## 修改

- 栅栏、玻璃板四向连接，墙的连接高度与柱体、栅栏门嵌墙状态、楼梯邻接形状，按世界派生状态处理。
- 木门、木活板门、栅栏门允许以关闭状态开始放置，随后通过正常使用动作打开；最终比较仍要求正确开关状态。
- 栅栏门打开时使用目标朝向交互，避免从另一侧打开导致门翻转朝向；交互后恢复玩家视角。
- 拉杆允许先放置再切换通电状态，沿用现有调整流程。
- 从 Diagonal Blocks 的公开转换注册表读取精确对应关系，仅兼容栅栏、玻璃板和墙这三类；不根据同名或同物品猜测对应关系。注册表首次使用时缓存，逐格比较不反射。
- 队列分类、最终比较和含水调整使用同一对应关系，避免将对角变体反复当成错误方块拆除。

材质、朝向、上下半部、含水和最终开关状态仍检查。铁活板门不能手动打开，不能依靠这次放宽放成任意开关状态；红石供电状态也没有整体忽略。邻接形状随世界变化，不要求保存投影里与当前周围环境矛盾的连接。

## 验证

使用真实 Minecraft 1.20.1 客户端、Java 17、Fabric Loader 0.18.4、Fabric API 0.92.2。分别运行不装对角模组和安装乌托邦同版本 Diagonal Fences / Windows 8.1.5 的独立世界；嵌套 Diagonal Blocks 为 8.0.6。没有使用整套乌托邦服务器作为此轮测试环境。

辅助模组使用实际 PrinterEngine，关闭准确放置协议和隔空放置，启用错误状态／错误方块拆除。场景由 22 个目标格组成，包含四向栅栏门、木门、木活板门、连续栅栏／墙／玻璃板、对角连接、含水栅栏，以及放在非完整方块上面的石英块。直接读取服务端最终状态，并持续 60 tick 检查是否产生重复操作。

旧 0.4.17 的规则对照重现了连接状态、关闭状态放置到打开目标、对角方块对应和含水调整失败；材质／方向等负例正常。新版运行结果及服务端状态保存在 [数据目录](data/placement-20261027/)。本次创造模式集成服务器测试覆盖正常放置与交互，不作为生存库存补货或整包服务器验收。

| 环境 | 最终结果 | 操作数 | 完成后的稳定观察 |
| --- | --- | --- | --- |
| 无对角模组 | 22 个目标格全部符合施工规则，四向栅栏门均已打开且朝向正确 | 28 | 60 tick 无新增操作 |
| Diagonal Fences / Windows | 同上，服务端生成对角玻璃板连接，含水对角栅栏完成 | 28 | 60 tick 无新增操作 |

四向门场景首次对角复测在窗口失焦后触发辅助测试器超时，最终快照中目标已放置，但未完成稳定观察。保留该轮 `focus-timeout-diagonal.json`；修正测试器将焦点等待单独计时后，用同一生产 JAR 重新运行通过。新增门占据原对角栅栏连接空间，因此最终辅助断言改查仍存在对角连接的玻璃板；早一轮场景已观察到对角栅栏连接。

`:fabric-1.20.1:build` 及适配检查通过；`:core:selfTest` 通过 139 项测试、2,513,993 条断言。辅助模组源码和复测步骤见 [checks/printer-placement](../../checks/printer-placement/README.md)。
